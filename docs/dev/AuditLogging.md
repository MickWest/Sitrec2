# Server audit logging

This page is for operators of a Sitrec server. Sitrec can write JSON records of
security events: certificate authentication, and the reads, writes and refusals of
its server APIs. Certificate mode always turns this on. In other modes it is off
until you enable it. The writer is `sitrecServer/audit.php`. It only writes the
records. The installing site must collect, protect, retain and monitor them, and
must supply incident response.

## Configuration

`AUTH_MODE=cert` always enables these events, and `AUDIT_LOG_ENABLED=false` cannot
disable them. For other authentication modes, set `AUDIT_LOG_ENABLED=true` to enable
the same API instrumentation. These are server environment settings, never browser
settings. The container entrypoint forwards them into the server environment. On
other installations, set them in `config/shared.env` and rebuild, or set them in the
PHP process environment.

`AUDIT_LOG_DESTINATION` selects one of two local delivery mechanisms:

| Value | Destination |
|---|---|
| `error_log` (default, including unset) | PHP's configured error logger. In the published Apache container this is collected through the container error stream. Configure a separate protected file or service at the PHP/server layer on other installations. |
| `syslog` | Local system logger, identity `sitrec-audit`, facility `AUTHPRIV`, priority `INFO`. The operating system collector must be available and configured to forward securely. The published container has no system logger, so use `error_log` there. |

The application accepts no audit filename or remote destination URL. It creates no
audit file under the webroot, uploads directory or cache. The operator must also
keep the **PHP error logger's own destination** outside those locations.

The public egress contract is the `audit.php` entry in
`scripts/egress-allowlist.json`, using the narrow `audit-metadata` data class. It
records the automatic authentication/API triggers and the local destinations
above. It does not authorize an unspecified remote collector. Before configuring
PHP, syslog, a container log driver or another agent to forward these records,
review the concrete destination, the same or a smaller field set, reader roles
and retention in the site's own inventory. Protect hashes and account/peer
identifiers as operational data; hashing does not make them anonymous. The
application does not enforce or verify downstream forwarding configuration.

Existing installations must merge the certificate resolver's audit call from
`config/config.php.example` into their locally maintained `config.php`; replacing
application files does not overwrite that local configuration. The current
template calls `sitrecAuditAuthentication()` after resolving a certificate.

## Record format

Every application record is one line: `SITREC_AUDIT ` followed by a JSON object
with schema `sitrec.audit.v1`. PHP, Apache or syslog may add text before or after
the record. Apache can append `, referer: <page URL>`. That URL can hold the page's
query string, which is not an audit field. The collector should read one JSON object
from the marker, ignore text after its closing brace, and remove the referer.

| Field | Meaning |
|---|---|
| `timestamp` | UTC timestamp with microseconds and a `Z` suffix |
| `request_id` | 128 random bits generated by the server for this PHP request; no incoming request ID is trusted |
| `instance`, `endpoint`, `method` | Server instance, script basename, and HTTP method; no URL or query string |
| `remote_addr` | Validated transport peer address. Behind a proxy this is the proxy, not the workstation. The record has no proxy trace ID. Match it to proxy logs by time, script name and HTTP status. |
| `actor_id` | Original application user ID, `0` for an unresolved/anonymous user, or `null` if identity resolution has not completed |
| `effective_user_id` | User whose context the operation uses; differs from the actor during administrator impersonation |
| `event`, `outcome`, `reason` | Fixed operation name, result, and machine-readable reason |
| `resource_sha256` | Full SHA-256 digest of the object key or logical resource identifier, when known; never the original value |
| `phase`, `http_status` | Request `start`/`finish` and final response status; absent on standalone authentication/decision events |
| `auth`, `identifier_sha256` | Authentication mechanism and hashed subject identifier on certificate events |

Object digests and user IDs are pseudonymous operational data, not anonymous data.
A low-entropy filename can be guessed and hashed. Restrict audit access accordingly.
Request bodies, credentials, certificates, cookies, authorization headers, share
links, filenames, metadata labels, coordinates and presigned URLs are not audit
fields. All output uses JSON encoding and bounded tokens. Unrecognized fields are
discarded. Client IP and correlation headers cannot overwrite server values.

## Application event inventory

| Endpoint / source | Events |
|---|---|
| `config.php` certificate identity resolver | `authentication`: accepted/refused and fixed refusal reason ([Installing Sitrec](Installing-and-configuring.md#client-certificate-authentication) lists them). The hashed identifier is present only if the resolver reached the identifier, so early refusals such as `no_certificate`, `chain_untrusted` and `expired` have none. |
| `user.php` | `authorization.impersonation`: written when a request has `testUserID` above 1. Accepted for an administrator. Denied otherwise; the request then continues as the caller and can finish `success`. Original and effective identity retained. |
| `config_paths.php?FETCH_CONFIG` | `configuration.read` |
| `rehost.php?getuser` | `identity.read` |
| `rehost.php` upload/delete | `object.upload`, `object.delete` |
| Presigned and multipart actions | `upload.authorize`, `upload.initiate`, `upload.complete` |
| `object.php`, `s3-proxy.php` | `object.resolve`, `object.read` |
| `getsitches.php` | `sitch.list`, `sitch.versions`, denied `authorization.version_list` (the request still lists the caller's own versions) |
| `settings.php` | `settings.read`, `settings.write` |
| `metadata.php` | `metadata.read`, `metadata.write`, `metadata.screenshot_versions`, `featured.read`, `featured.write`, `templates.read`, `templates.write` |
| `shortener.php` | `share.create` |
| `admin_info.php` | `administrator.user_read`, failed `administrator.lookup` |
| `proxy.php`, `customWindProxy.php` | `catalogue.read`, `wind.read` |
| `channels.php` (not in the secure build, which `npm run build-secure` makes) | `channel.read`, `channel.write` |
| `s3-proxy.php` signed fetch, `proxy.php` refresh, shared cURL helper | Failed `storage.fetch`, with reason `upstream_error`, or `tls_error`/`transport_error` from the shared helper. `s3-proxy.php` can then read the object through its unsigned fallback and finish `success`. A failure of that fallback writes no `storage.fetch`, and shows only in the `object.read` finish record. |

Each instrumented API request records an attempt and a completion at shutdown. The
start record is `attempted`/`request_received`. The finish record takes the first
row that matches:

| Finish condition | `outcome` / `reason` |
|---|---|
| Fatal runtime error | `failure` / `runtime_error` |
| Status 401 or 403 | `denied` / `authorization_failed`. Status 401 means that the endpoint requires a known user and the request has none. Status 403 is a refusal by the endpoint, and the caller can be anonymous (`actor_id` 0). `s3-proxy.php` copies the storage status, so its 403 can come from storage. For a refused certificate, read the `authentication` record. |
| Status 429 | `denied` / `rate_limited` |
| Status 400, 405, 413, 415 or 422 | `rejected` / `invalid_request` |
| Any other status of 400 or above | `failure` / `http_error` |
| Any other status | The result that the operation recorded, or `failure` / `incomplete` if it recorded none |

The first five rows replace any result that the operation recorded. Successful
completion must be marked by the operation itself, so an early return with HTTP 200
alone is **not** a success. A recorded operation failure cannot be replaced by a
later success marker.

A successful presigned URL event means **permission to upload was issued**, not
that bytes reached storage. Only multipart completion or an upload handled by the
server can record that operation's completion. An `object.read` success means the
server finished streaming; it does not prove the browser saved or viewed the result.
An `object.resolve` success means only that the server returned a URL. If that URL
is presigned or public, the browser reads from storage directly, so no `object.read`
record exists and only storage data events show the read.
Catalogue cache responses distinguish `stream_finished`, `not_modified` and
`redirect_issued`; a redirect records only the issued redirect, not the later download.
Multi-object operations are summarized per request and are not transactional:
failure can follow partial changes. Storage data events supply per-object detail.

## Other layers in the log inventory

| Layer | Records and destination | Access / retention owner |
|---|---|---|
| TLS proxy / load balancer | Handshake acceptance/refusal, revocation failures, connection and HTTP access logs; the configured protected collector or log bucket | Operator. Include refusals that occur before PHP is reached. Filter query strings/capabilities and certificate subjects according to local data policy. |
| Apache / PHP | Access logs, startup failures, warnings and uncaught exceptions; configured server error/access destinations | Operator. Disable browser error display; restrict diagnostics because these can contain paths and request details. |
| Application | The JSON events above, through PHP's logger or local syslog | Operator. Application has no read/delete/retention API for these records. |
| Object storage | Object reads/writes/deletes and service role identity; storage data-event collector | Operator. Includes direct presigned operations and storage identifiers absent from application events. |
| Infrastructure | Administrative configuration changes, network flows and deployment events; infrastructure audit collector | Operator. Trust-store changes, user-map edits and host configuration changes happen outside PHP. |
| Browser | Browser console and client-managed storage; no security audit export | Do not treat the console as a protected audit trail or assume browser-local file operations reach the server. |

The supplied AWS configuration routes the container stream to its application log
group with `log_retention_days`, enables load-balancer access and connection logs,
and enables management and data-bucket object events plus VPC flow logs. It does
not prove the settings of any running installation. The supplied configuration sets
no expiry on the log bucket, so its retention is a separate decision from the
application log group's retention.

Before accepting a deployment, record its concrete destinations, retention periods,
reader/administrator roles, deletion restrictions, synchronized time source,
transport encryption, review owner, and alert routing. Configure alerts for audit
delivery failures, unexpected gaps in the stream, repeated refusals and privileged
actions. Verify ingestion and deletion restrictions using the application's actual
service identity and a separate operator identity. A local log file alone does not
protect evidence from an application or host compromise.

## Failure and coverage limits

If an unknown destination is configured, Sitrec drops the record and emits
`SITREC_AUDIT_DELIVERY_FAILED` through PHP's error logger. It does not include the
lost record or the destination value in that diagnostic. The absence of this
diagnostic does not prove delivery: PHP's `error_log()` reports success even when it
cannot open its log file. Detect delivery failures at the collector, from gaps in
the stream. Business operations continue; an already completed upload cannot be
rolled back by an audit delivery failure. Sites requiring durable acknowledgment
before a write must add that control before deployment. PHP's error logger and local
syslog acknowledging a write do **not** establish receipt by the remote collector.

Abrupt process termination, resource exhaustion, a failed collector, or a full disk
can lose events. Start records can help find missing finishes but are not a durable
transaction log. Match start and finish records by `request_id`, because `metadata.php`
can change the event name during a request. The collector needs independent health
monitoring, buffering, capacity limits and secure forwarding. The application does
not implement log rotation, immutable storage, clock synchronization, cryptographic
log signing or alert delivery.

Auditing records a read. It does not control the read. A valid complete object key
still acts as a read capability (see
[File rehosting and object references](FileRehosting.md#stable-object-references)).
Enabling auditing resolves identity for attribution; it does not add per-object
authorization or turn an unmapped certificate into an authorized user. Certificate
deployments still require the protected proxy path, trust-store policy and suitable
application access rules.
Unauthenticated TLS attempts are recorded at the proxy. Static assets, direct local
file downloads, browser exports and the other APIs of a standard (non-secure) build
are outside this PHP event inventory. In a standard build, forum authentication
remains owned by the forum; these events do not replace its login/session audit log.

## Verification

`tests/auditLogging.test.js` sends real HTTP requests to the PHP endpoints against
isolated identity/storage fixtures. It verifies success, refusal, failed writes,
multipart behavior, original/effective identity, correlation, content exclusion,
log injection defenses and the diagnostic for an unknown destination. The suite runs
under PHP's built-in server, does not exercise `syslog`, and skips when PHP is not
installed. `tests/authCertMode.test.js` exercises the certificate resolver with a
temporary certificate authority. The secure-build server allowlist requires the audit
writer to be packaged.
